# TRIPA 팀 공통 규칙 (팀원 모두의 Claude Code가 읽는 파일)

이 리포는 3인 팀 프로젝트입니다: 🟦 프론트 임영준(`front` 브랜치), 🟧 백엔드 이수한(`back`), 🟩 AI 서지윤(`ai`).
사용자에게 보이는 내용은 한국어로 씁니다.

## 세션을 시작하거나 사용자가 `git pull`을 했을 때
1. 사용자가 어느 파트인지 모르면 먼저 물어봅니다(현재 브랜치 이름이 `front`/`back`/`ai`면 그것으로 판단).
2. `docs/TEAM_UPDATES.md`의 최신 항목들을 읽고, **그 사용자 파트의 체크리스트**를 요약해 알려줍니다.
3. 방금 pull한 변경이 있으면 `docs/PULL_CHECKLIST.md`의 표대로 바뀐 파일을 분류하고, 사용자 파트에 영향이 있는 것만 "무엇이 바뀌었고, 무엇을 확인·수정해야 하는지"로 정리합니다(`git log ORIG_HEAD..HEAD`, `git diff --stat ORIG_HEAD..HEAD`).
4. 화면 모양은 목업(https://claude.ai/artifact/BqZEgyPi2NH36UjyHwbYBk, 리포 사본 `docs/mockup/tripa-mockup.html`), 응답 키는 리포 최상위 `mock.json`이 기준입니다. 목업은 참고용이며 프론트 코드로 그대로 옮기지 않습니다.

## 지킬 것
- AI는 프로젝트 기능 코드를 대신 작성하지 않습니다. 개념·순서·"어느 파일의 어느 부분"과 힌트만 줍니다. 사용자가 코드를 붙여넣으면 문제 줄을 힌트로 알려줍니다. 문서·설정 정리는 사용자가 명시적으로 부탁할 때만 합니다.
  - **예외 (11/06):** 사용자가 직접 하기 어려워서 "직접 수정해 줘", "Claude Code로 고쳐 줘"처럼 **분명히 부탁하면** 그 사용자 브랜치에서 코드를 고쳐도 됩니다.
    - 고치기 전에 어느 파일을 어떻게 바꿀지 짧게 먼저 알려 줍니다.
    - 고친 뒤 무엇을 왜 바꿨는지 쉬운 말로 설명하고, 확인 방법(`python manage.py check`, 열어 볼 화면)을 알려 줍니다.
    - 커밋·push·PR은 사용자가 확인하고 직접 하게 둡니다(부탁받으면 도와도 됨). 아래 브랜치·응답 키 규칙은 그대로 지킵니다.
    - 부탁하지 않았으면 기존 방식(개념·힌트)으로 돕습니다. 어느 방식으로 할지는 사용자가 고릅니다.
    - 작업별 설명과 부탁 문장: 팀 진행도 "주간 가이드" 탭 (https://claude.ai/artifact/1Lwf6NtqDRyUH16a1ZFPMb#guide)
- **수업에서 안 배운 기능·코드는 자세히 설명합니다 (11/09).** 힌트를 줄 때도, 직접 고쳐 줄 때도 같아요. 처음 보는 문법·라이브러리 기능·장고 기능·CSS 규칙이 나오면 아래 네 가지를 짧게라도 꼭 적습니다.
  1. **무엇인지** 한 줄 (예: "`collections.Counter`는 몇 번 나왔는지 세 주는 사전")
  2. **왜 여기서 쓰는지** (이 코드에서 맡는 일)
  3. **작은 예시**: 넣으면 → 무엇이 나오는지 (예: `Counter(['a','b','a']).most_common()` → `[('a', 2), ('b', 1)]`)
  4. **흔한 실수** (예: 줄 끝 쉼표가 튜플을 만듦, `{ }` 밖의 `'키': 값`, 닫는 `{% endif %}` 빠짐, CSS는 더 구체적인 선택자가 이김, 정적 파일 `?v=` 번호를 안 올려 예전 파일이 보임)
  - 수업에서 배운 것(아래)은 몇 일차인지 짚고 짧게 설명해도 됩니다. **배웠는지 확실하지 않으면 자세히 쪽으로** 합니다.
    - 08/05·08/06 13·14일차 집계·GROUP BY · 08/10·08/11 16·17일차 트리거 · 08/20~08/24 23~25일차 SQLAlchemy·pandas · 08/24·08/25 25·26일차 공공 API·BeautifulSoup · 09/02 32일차 Chart.js · 09/30·10/01 49·50일차 임베딩·RAG · 10/01·10/07 50·53일차 Streamlit · 10/02 51일차 Function Calling · 10/06 52일차 LangChain 라우팅 · 10/08·10/13·10/20 54·56·61일차 FastAPI
  - 설명은 코드 옆 주석이 아니라 답변에 씁니다(코드 주석은 그 기능이 무엇인지 한두 줄만).
  - **보기 좋게 (11/09):** 설명할 때 코드를 같이 보여 주고, VS Code처럼 색이 나뉘게 **언어를 붙인 코드 블록**으로 씁니다.
    - 파이썬 ` ```python `, 장고 템플릿 ` ```django `(또는 ` ```html `), CSS ` ```css `, 자바스크립트·React ` ```javascript `/` ```jsx `, 터미널 명령 ` ```powershell `/` ```bash `, JSON ` ```json `
    - **고칠 줄은 ` ```diff ` 블록**으로: `-` 원래 줄(빨강), `+` 바꾼 줄(초록). 몇 번째 줄인지는 블록 위에 `파일:줄`로 적습니다.
    - 함수·변수·파일 이름은 글 안에서 `백틱`으로 감싸 글과 코드를 구분합니다.
    - 예시의 "넣으면 → 나오는 것"은 코드 블록 안 주석으로 결과를 적습니다 (예: `Counter(['a','b','a']).most_common()  # [('a', 2), ('b', 1)]`).
- `main`에 바로 push하지 않습니다. 자기 브랜치에서 작업하고 PR로 합칩니다(합치기는 팀장).
- 기존 응답 키와 함수 이름은 바꾸지 않고 추가만 합니다. 바꿔야 하면 세 사람 합의 후 `mock.json`과 `docs/TEAM_UPDATES.md`부터 고칩니다.
- **여러 사람이 같이 쓸 새 함수·응답 키(11/09 결정):** 먼저 작업하는 사람이 이름·받는 값·돌려주는 값을 정하고, 기능을 다 만들기 전이라도 `docs/TEAM_UPDATES.md`(응답 키면 `mock.json`도)에 먼저 적어 작은 PR로 바로 공유합니다. 다른 사람은 그 정의를 그대로 씁니다. 작업을 시작할 때 TEAM_UPDATES에 이미 정해진 같은 용도의 함수·키가 있는지 먼저 확인하도록 안내합니다.
- 다른 파트에 영향을 주는 변경을 올릴 때는 `docs/TEAM_UPDATES.md`에 항목을 추가하고 PR 템플릿의 '다른 파트 영향'을 채우도록 안내합니다.
- `.env`의 값(API 키, 비밀번호)은 읽거나 출력하지 않습니다.
